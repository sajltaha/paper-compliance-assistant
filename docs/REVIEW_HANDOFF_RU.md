# Проверка исправленного пакета перед слиянием

Это инструкция для реальной проверки, а не уже полученное ревью.

Кайсару нужно открыть PR ветки PCA-16-audit-fixes, прочитать изменения и проверить весь пакет, а не только количество файлов. Указать проверенный SHA и собственные выводы из своего аккаунта. Не выдавать AI-проверку за независимую человеческую проверку.

1. Proposal: соответствуют ли проблема, границы, ожидаемые результаты и роли согласованной теме; что исключено из MVP.
2. Литература: открыть ключевые источники, сверить ограничения и влияние на проект; выбрать хотя бы два конкретных решения и объяснить, какие источники их поддерживают.
3. FR/NFR: проверить источник/стадию критериев, четыре состояния результата, существование evidence, DOCX anchors, conversion gate и точный лимит 20 MiB.
4. Технологии: оценить аргументы PostgreSQL/SQLite и Docling/GROBID через локальный запуск и проверяемость качества. Предложение не равно окончательному выбору.
5. Архитектура: проследить сохранение и повторное открытие run; удаление зависимых данных; подтверждение внешней передачи; сопоставить API и диаграмму.
6. Запустить `node tests/prototype_smoke.cjs`; при доступном Go запустить `go test ./...` из backend. Показать синтетический интерфейс и объяснить границы validator.

В отзыве зафиксировать фактические замечания с файлами/фрагментами, решение по каждому и проверенный результат. Если замечаний нет — объяснить, какие проверки выполнены и почему изменение принято. Не публиковать заготовленный отзыв от имени проверяющего. После замечаний автор исправляет PR, проверяющий повторно проверяет изменённый SHA, затем выполняется merge. Позднее чтение старых PR не превращается в review до их исторического merge.

Для руководителя показать обновлённый отчёт, границы MVP, требования, технологические trade-offs, корпус/метрики и оставшийся внешний критерий актуальности. Попросить указать реальные решения и замечания. Отдельно уточнить, принимается ли анализ открытых данных вместо строки о 3–5 обсуждениях. Записать фактическую дату ответа, рассмотренные материалы, решение и приватную ссылку на оригинал. Не приписывать подробного одобрения общему ответу.
